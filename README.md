# ig-autopost

Google Drive に置いた原稿と写真を、決めた時刻に Instagram へ自動で投稿する。
GitHub Actions の上で 15 分ごとに動き、**「承認」と書かれた原稿だけ**を出す。

```
Drive: 01_素材/店のフォルダ/写真        ┐
Drive: 02_原稿/原稿_店の名前（承認）    ┘→ GitHub Actions → Instagram
                                              │
        原稿は「済_」に改名、素材は 03_投稿済み へ移動
```

## 先に知っておくこと

- **このコードは、本物の Instagram と Google Drive に対してはまだ一度も動かしていない。**
  手元のテスト（131 本）は全部通っているが、相手はにせものの Drive と Instagram。
  最初の 1 本は、下の「5. 確認」を順に踏んでから出すこと。
- **リポジトリは Public（公開）で作る必要がある。** Instagram は写真を URL から取りに来るので、
  写真を誰でも取れる場所に置かなければならない。その置き場にこのリポジトリを使っている。
  公開されるのは、コード、投稿直前の写真、点検（dry-run）で出る切り抜き写真とキャプション、実行ログ。
  **鍵（トークン類）は Secrets に入れるので公開されない。**
- 対応しているのは**写真 1 枚の投稿とカルーセル（10 枚まで）**。リールとストーリーズは未対応。
- **位置情報タグは付かない。** この方式の API では付けられない。投稿後に Instagram アプリで足す。
- 写真は**縦長なら 4:5 に切られる**（API が 3:4 を受け付けないため）。カルーセルは全部が 1 枚目と同じ比率になる。
- 投稿の時刻は、予約より**数分〜数十分遅れる**ことがある（GitHub 側の都合）。

## 準備（合計 1〜2 時間）

画面の文言は各サービスの更新で変わることがある。見つからないときは近い名前を探す。

### 近道：`setup.sh` にまとめてやらせる

手順 1・2・4・5 は、ターミナルでこのフォルダに入り、`bash setup.sh` を実行すればまとめて済む。
自分でやるのは、**手順 0 と、手順 3（Instagram のトークンを作る）だけ**になる。

```bash
brew install gh && gh auth login                      # GitHub。まだなら
brew install --cask gcloud-cli && gcloud auth login   # Google。まだなら
bash setup.sh
```

- 途中で 3 回、手を止める：公開リポジトリを作ってよいかの確認（`y`）、
  Instagram のトークンの貼り付け（画面には出ない）、Drive の共有が済んだかの確認（Enter）
- Google の鍵は、作ってすぐ GitHub に渡して消す。手元にも画面にも残らない
- 途中で止まったら、もう一度 `bash setup.sh`。済んだところは飛ばして続きから進む
- `gcloud` を入れたくないときは、手順 2 の 1〜4 を画面でやって
  `KEY_FILE=~/Downloads/鍵.json bash setup.sh` で渡す
- `setup.local.env` には Drive のフォルダ ID が入っている（公開側には入らない）

終わったあとに使うもの：

| コマンド | すること |
|---|---|
| `bash setup.sh check` | 接続の確認だけ |
| `bash setup.sh dry-run` | 点検だけ。切り抜き後の写真とキャプションを `preview_out` に置いて開く |
| `bash setup.sh post` | 承認済みで日時を過ぎた原稿を、今すぐ投稿する |
| `bash setup.sh token` | Instagram のトークンを作り直す（下の「トークンを生成で作れないとき」） |

`GH_PAT`（手順 4 の最後）と、定期実行のスイッチ（手順 6）は `setup.sh` ではやらない。

**「トークンを生成」で作れないとき**（押しても Instagram のホームが出るだけ、など）

`setup.sh` の「4/5」で `n` を選ぶか、`bash setup.sh token` を実行すると、ブラウザの許可からトークンを作る。
聞かれるのは、Meta の画面の「Instagramビジネスログインを設定する」→「ビジネスログイン設定」にある
**InstagramアプリID** と **Instagram app secret**。同じ場所の「OAuthリダイレクトURI」に `https://localhost/` を入れて保存しておく。
許可を押すと「このサイトにアクセスできません」という画面になるので、そのアドレスバーの中身を貼り付ける。
トークンは画面に出ず、そのまま GitHub に登録される。

以下は、同じことを手でやる場合の手順。

### 0. Instagram 側

アカウントが**公開**で、**プロアカウント（クリエイター）**になっていること。

### 1. GitHub にリポジトリを作る

1. GitHub で新しいリポジトリを **Public** で作る（名前は何でもいい）
2. このフォルダの中身をそのまま入れる

```bash
git init -b main
git add -A
git commit -m "first commit"
git remote add origin https://github.com/<自分>/<リポジトリ>.git
git push -u origin main
```

`*.json` は `.gitignore` で除外してある。Google の鍵ファイルをうっかり入れないため。

この時点では何も投稿されない。定期実行は、手順 6 でスイッチを入れるまで動かない。

### 2. Google：Drive を読むための鍵を作る

課金の設定は不要。Google アカウントの 2 段階認証は必要。

1. <https://console.cloud.google.com/> でプロジェクトを新しく作る
2. 「API とサービス」→「ライブラリ」→ **Google Drive API** を有効にする
3. 「IAM と管理」→「サービス アカウント」→ 作成（ロールは付けなくていい）
4. 作ったサービスアカウント →「キー」→「鍵を追加」→ **JSON** → ファイルが落ちてくる
5. Google Drive で、原稿と素材が入っている一番上のフォルダを、
   サービスアカウントのメールアドレス（`…@….iam.gserviceaccount.com`）に **編集者** で共有する

### 3. Meta：Instagram に投稿するためのトークンを作る

自分のアカウントに投稿するだけなら、審査もビジネス認証も Facebook ページも要らない。
アプリは「開発モード」のままでいい。

1. <https://developers.facebook.com/apps/creation/> でアプリを作る。
   ユースケースは「Instagram でメッセージとコンテンツを管理」。ビジネスポートフォリオは省略できる
2. アプリのダッシュボード →「Instagram」→「Instagram ログインによる API 設定」
3. 「アクセストークンを生成」→ 自分の Instagram アカウントを追加（Instagram へのログインを求められる）
4. 招待の承認を求められたら、instagram.com の「設定」→「アプリとウェブサイト」→「テスターへのご招待」で承認する
5. 「トークンを生成」→ 出てきた文字列をコピーする（60 日有効。延長は自動でやる）

必要な権限は `instagram_business_basic` と `instagram_business_content_publish`。

### 4. GitHub に鍵と設定を入れる

リポジトリの「Settings」→「Secrets and variables」→「Actions」。

**Secrets タブ**

| 名前 | 値 |
|---|---|
| `IG_ACCESS_TOKEN` | 手順 3 のトークン |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | 手順 2 の JSON ファイルの中身をそのまま全部 |
| `GH_PAT` | 下で作る個人アクセストークン |

**Variables タブ**

| 名前 | 値 |
|---|---|
| `DRIVE_MATERIAL_ID` | `01_素材` フォルダの ID |
| `DRIVE_DRAFT_ID` | `02_原稿` フォルダの ID |
| `DRIVE_POSTED_ID` | `03_投稿済み` フォルダの ID |

フォルダの ID は、Drive でフォルダを開いたときの URL の `folders/` より後ろの部分。

**`GH_PAT` の作り方**（Instagram のトークンを入れ替えるために使う）

GitHub の「Settings」→「Developer settings」→「Personal access tokens」→「Fine-grained tokens」→ 新規作成。

- Repository access：このリポジトリだけ
- Repository permissions：**Secrets** を **Read and write**
- 有効期限：選べる中で一番長くする。**切れる日をカレンダーに入れておく。**
  これが切れると Instagram のトークンを入れ替えられなくなり、最長 60 日後に投稿が止まる

### 5. 確認（ここを飛ばさない）

リポジトリの「Actions」タブ →「publish」→「Run workflow」。

1. **mode = check** で実行する。次の 5 行に ✓ が付けば、つながっている
   - Drive：3 つのフォルダが読める（3 行）
   - Instagram：自分のアカウント名で接続でき、最近の投稿が読めた
   - 写真の置き場：media ブランチに置いて、外から取れた
2. **mode = dry-run** で実行する。何も投稿されず、何も書き換わらない
   - 実行結果のページに、原稿ごとの点検結果と「直すところ」が出る
   - ページ下の「Artifacts」から `preview` を落とすと、**切り抜き後の写真**と `caption.txt` が入っている。
     写真の切れ方と色、キャプションの改行が崩れていないかを見る
   - 下書きのままの原稿も点検される（承認する前に切れ方を見られる）

### 6. スイッチを入れる

Variables タブに `AUTOPOST_ENABLED` を作り、値を `true` にする。ここから 15 分ごとの定期実行が動く。

**止めたいとき**は `AUTOPOST_ENABLED` を `false` に戻す。それだけで定期実行は何もしなくなる。

最初の 1 本は、投稿されたあとに Instagram で実物を確認する。

## 毎回の使い方

### 原稿の書式

原稿（Google ドキュメント）の中に、次の 2 つのかたまりがあること。
`===` の行は機械が目印にしているので、消したり書き換えたりしない。

```
=== 投稿設定 ===
状態: 下書き
日時: 2026-10-08 21:00
形式: カルーセル
素材フォルダ: ミクロとくじら
写真: IMG_4040, IMG_4036, IMG_4032
=== 投稿設定ここまで ===

=== キャプション ===
（ここに書いたものが、そのまま投稿される）
=== キャプションここまで ===
```

- **状態**：ちょうど `承認` と書いたものだけが投稿される。`承認済み` や `OK` では動かない
- **日時**：日本時間。`2026-10-08 21:00` の形
- **素材フォルダ**：`01_素材` の中のフォルダ名と同じにする
- **写真**：カンマで区切って **1 行に**書く。並べた順に投稿される。HEIC のままで読める
  - 拡張子は省ける（`IMG_4040`）。拡張子まで書いたら、その名前のファイルだけを使う（`表紙.png`）
  - 同じ名前に当てはまるファイルが 2 つあると、勝手には選ばずに止まる

### 承認するときにやること

1. キャプションを読んで、味の感想を足し、値段などを確認する
2. `【要確認】` と `___` を全部消す（残っていると投稿されない）
3. 「状態」を `承認` に書き換える

### 原稿のファイル名で状態が分かる

| ファイル名 | 意味 |
|---|---|
| `原稿_…` | 下書き、または予約済み（ファイルの「詳細」の説明欄に予約日時が出る） |
| `済_原稿_…` | 投稿した。説明欄に投稿の URL が入る。素材フォルダは `03_投稿済み` に移る |
| `要対応_原稿_…` | 止めた。説明欄に理由と、次にやることが書いてある |

**`要対応_` になったら**：説明欄を読む。たいていは、原稿を直してファイル名の先頭の `要対応_` を消せば、
次の実行でもう一度見に行く。GitHub からも失敗のメールが届く。

### 表紙に文字を入れたいとき、写り込みを消したいとき

加工した画像を素材フォルダに入れて、「写真」の先頭にその名前を**拡張子まで**書く（例：`表紙.jpg`）。
元の写真と名前がかぶらないようにする。

## 止まる条件（安全側に倒してある）

次のどれかに当たると、投稿せずに `要対応_` にする。

- キャプションに `要確認` か、穴埋めの下線（`__`、`＿`）が残っている
- `#` が 6 個以上、キャプションが 2,200 文字超、写真が 11 枚以上
- 投稿設定の中に読めない行がある（写真の一覧が途中で改行されている、など）
- 素材フォルダや写真が見つからない、同じ名前のものが 2 つある、写真が壊れている
- 予約の日時から 12 時間以上過ぎている（遅れて突然出るのを防ぐ）
- Instagram が原稿や写真を受け付けなかった
- まったく同じキャプションの投稿が、すでに自分のアカウントにある

一方、Drive や Instagram の一時的な不調、トークン切れは、原稿のせいにしない。
原稿はそのままにして次の実行でやり直す。失敗のメールは最初の 1 回と、その後は 6 時間おきに届く。
不調が続いて予約から 12 時間を過ぎたら、上の条件で `要対応_` になる。

準備の途中で原稿が書き換えられた場合（承認を取り消した、キャプションを直した）は、
その回は公開せず、次の実行で読み直す。

## 二重に投稿しないための歯止め

1. 公開の直前に原稿へ印を付ける。公開できたか分からないまま終わった場合は、**自動ではやり直さず**、
   `要対応_` にして人に確認を求める
2. 1 つの素材フォルダは 1 回しか使えない。承認済みの原稿が 2 本、同じ素材フォルダを指していたら、
   どちらが本物か分からないので**両方とも**止める（原稿をコピーして承認のまま置いてしまった場合など）
3. 公開の前に毎回、自分の最近の投稿（新しい順に 50 件）を見る。空白や改行の違いを除いて
   **まったく同じキャプション**の投稿があれば、投稿せずに `要対応_` にして判断を求める
4. 一度公開を試みた原稿については、さらに 200 件前までさかのぼり、キャプションの先頭 150 文字が
   同じ投稿があれば「前回のが出ていた」とみなして `済_` にする

同じ素材でもう一度投稿したいときは、新しい素材フォルダを作って写真を入れ直し、キャプションを変える。

## 運用で気をつけること

- **トークンは 60 日で切れる。** `refresh-token` が月 2 回、自動で延長して入れ替える。
  これが失敗したメールが来たら放置しない。切れたら手順 3 で作り直して `IG_ACCESS_TOKEN` に入れる
- `refresh-token` は延長の前に、`GH_PAT` で本当に書き込めるかを試す。そのとき Secrets に
  `AUTOPOST_PAT_CHECK` という確認用の項目ができる（中身は日時だけ。消さなくていい）
- **60 日間リポジトリに動きがないと、GitHub が定期実行を止める。** `refresh-token` の中で
  有効化し直しているが、確実ではない。止まっていたら「Actions」タブで Enable する
- 1 日に API で投稿できる数には上限がある（50〜100 本）。普通に使う分には届かない
- `requirements.txt` は、間接的に入るものまで含めて版と中身（ハッシュ）を固定してある。
  上げるときは `requirements.in` を書き換えて作り直し、テストを通してから

## 写真にしていること

- HEIC・PNG・JPEG を JPEG にそろえる。向きを直す
- 色を sRGB に変換する（iPhone の写真は Display P3 で、変換しないとくすんで見える）
- 位置情報を含む付帯情報をすべて落とす
- 幅 1440 まで縮め、8MB を超えないようにする

## テスト

```bash
pip install --require-hashes -r requirements.txt
pip install pytest
python -m pytest -q
```

Drive も Instagram も使わずに、次のことを確かめている。

- 原稿の読み取り（Google ドキュメントの書き出しの癖を含む）と、止める条件
- 写真の変換（HEIC、向き、色、位置情報の削除、比率、サイズ）
- 投稿する／待つ／止めるの分かれ方、二重投稿をしないこと、あいまいな名前を勝手に選ばないこと
- Instagram と Drive に送る内容の形、エラーの扱い（トークンがログに出ないこと）
- 写真を media ブランチに置く処理

```
autopost/instagram.py   Instagram API
autopost/main.py        全体の流れ（run / dry-run / check）
autopost/refresh.py     トークンの延長
.github/workflows/      定期実行の設定
setup.sh                初期設定をまとめて行う（上の「近道」）

```
